# 일일 수집결과 Gmail 보고서 설계

## 1. 목적

수집기별 실행 감사 이력을 공통 모델로 조회하여 전일 수집 결과를 요약하고, 개인 Gmail 계정의 OAuth 2.0 인증을 사용해 운영 수신자에게 일일 보고서를 자동 전송한다.

보고서는 다음 정보를 제공한다.

- 전체 요약: 전체 수집기 중 성공 수집기 수(예: `4/5 실행 성공`)
- 수집기별 실행 이력
- 실패, 부분 실패, 중단, 미실행, 조회 실패 수집기 강조

## 2. 범위

### 2.1 포함

- 기존 FastAPI 수집기 어댑터와 공통 `CollectorRun` 모델을 재사용한 감사 이력 조회
- 전일 KST 기준 일일 집계와 선택적인 보고일·수집기 필터
- HTML 본문과 텍스트 대체 본문 생성
- Gmail API를 통한 메일 전송
- 개인 Gmail OAuth 2.0 최초 인증과 갱신 토큰 기반 무인 인증
- `.env` 기반 To/Cc 수신자 설정
- 로컬 상태 파일을 이용한 중복 발송 방지와 `--force` 재발송
- Python CLI, Windows 배치 파일, 작업 스케줄러 운영 절차
- 단위·통합 테스트와 한국어 운영 문서

### 2.2 제외

- FastAPI 메일 발송 엔드포인트와 웹 발송 버튼
- 감사 테이블 및 업무 데이터 변경
- 제어 DB에 발송 상태 저장
- 원문 예외, URL, HTML, 인증정보, DB 연결정보의 메일·로그 노출
- Gmail 이외 메일 공급자 지원
- 첨부 파일 형태의 별도 보고서 생성

## 3. 기본 원칙

- 수집기별 DB 스키마 차이는 기존 FastAPI 어댑터 내부에서 처리한다.
- 보고 모듈은 수집기별 감사 테이블을 직접 알지 않고 공통 모델만 사용한다.
- 감사 DB와 업무 DB는 조회만 하며 보고서 생성·전송 과정에서 변경하지 않는다.
- 메일 본문과 로그에는 정제된 상태·오류 범주만 포함한다.
- 배치 파일은 실행 진입점만 담당하고 집계·전송 로직은 Python 모듈에 둔다.
- Gmail 전송 성공이 확인된 뒤에만 중복 방지 상태를 기록한다.
- 기능 구현은 테스트 우선으로 진행한다.

## 4. 전체 구조

```text
Windows 작업 스케줄러
  -> scripts/send_daily_collection_report.bat
  -> Python 보고서 CLI
       -> 기존 설정과 수집기 어댑터 조립
       -> 전일 00:00~24:00 KST 실행 이력 조회
       -> 수집기별 결과 및 전체 성공률 계산
       -> 텍스트 + HTML 메일 작성
       -> Gmail API 전송
       -> 로컬 상태 파일에 발송 완료 기록
```

구성 요소의 책임은 다음과 같다.

| 구성 요소 | 책임 |
| --- | --- |
| 조회 계층 | 기존 어댑터를 통해 보고 범위의 실행 이력을 공통 모델로 조회 |
| 집계 계층 | 수집기별 대표 상태, 전체 성공률, 상태별 건수, 실행 이력 계산 |
| 표현 계층 | 하나의 보고서 모델을 HTML과 텍스트로 렌더링 |
| Gmail 계층 | OAuth 자격 증명 갱신, MIME 메시지 생성, Gmail API 전송 |
| 상태 계층 | 발송 완료 키 조회와 원자적 기록 |
| CLI 계층 | 날짜·수집기 필터·강제 재발송·종료 코드 조정 |
| 배치 파일 | 프로젝트 가상환경의 CLI 호출과 종료 코드 전달 |

## 5. 실행 인터페이스

기본 실행은 현재 KST 날짜의 전날을 보고일로 사용하고 등록된 모든 수집기를 대상으로 한다.

```text
python -m monitoring_api.daily_report send
python -m monitoring_api.daily_report send --report-date 2026-09-17
python -m monitoring_api.daily_report send --collector-id smartplace --collector-id hmr
python -m monitoring_api.daily_report send --report-date 2026-09-17 --force
python -m monitoring_api.daily_report authorize
```

- `send`: 보고서 생성과 Gmail 전송
- `authorize`: 최초 1회 브라우저 동의를 수행하고 갱신 가능한 OAuth 토큰을 안전한 외부 경로에 저장
- `--report-date`: KST 기준 보고일 재지정
- `--collector-id`: 대상 수집기 제한, 여러 번 지정 가능
- `--force`: 이미 성공적으로 발송한 동일 보고일·동일 범위 보고서 재발송

배치 파일은 `send` 명령과 전달받은 추가 인자를 그대로 실행하고 Python 종료 코드를 작업 스케줄러에 반환한다. 평상시 배치 실행은 브라우저를 열지 않는다.

## 6. 설정과 비밀정보

`.env.example`에는 값이 없는 설명용 키만 추가하며 실제 값은 커밋하지 않는다.

| 설정 | 용도 |
| --- | --- |
| `MONITORING_REPORT_GMAIL_CLIENT_ID` | 개인 Gmail OAuth 클라이언트 ID |
| `MONITORING_REPORT_GMAIL_CLIENT_SECRET` | 개인 Gmail OAuth 클라이언트 비밀 |
| `MONITORING_REPORT_GMAIL_TOKEN_FILE` | 갱신 토큰을 포함한 OAuth 토큰 파일의 저장소 외부 경로 |
| `MONITORING_REPORT_EMAIL_TO` | 쉼표로 구분한 To 수신자 |
| `MONITORING_REPORT_EMAIL_CC` | 쉼표로 구분한 선택적 Cc 수신자 |
| `MONITORING_REPORT_SENDER` | Gmail API에서 사용할 발신 계정 주소 |
| `MONITORING_REPORT_STATE_FILE` | 중복 방지 상태 파일 경로 |

Gmail 권한 범위는 전송에 필요한 최소 범위인 `gmail.send`만 요청한다. 토큰 파일과 상태 파일의 기본 위치를 저장소 내부로 자동 결정하지 않으며, 운영자가 명시한 절대 경로를 사용한다. 로그, 예외 메시지, 테스트 스냅샷에는 클라이언트 비밀과 토큰을 포함하지 않는다.

## 7. 보고 범위와 실행 조회

보고일 `D`의 조회 범위는 `D 00:00:00 Asia/Seoul` 이상 `D+1 00:00:00 Asia/Seoul` 미만이며, 어댑터 호출 전 UTC로 변환한다.

기본 보고는 등록된 모든 수집기를 대상으로 한다. `--collector-id`가 있으면 등록 여부를 검증하고 지정된 수집기만 조회한다. 각 어댑터의 실행 목록 계약을 사용하므로 보고 계층에는 수집기별 SQL을 추가하지 않는다.

각 수집기 조회는 서로 격리한다. 일부 조회가 실패해도 나머지 수집기의 보고서를 생성하며 해당 수집기는 `조회 실패`로 표시한다. 모든 수집기 조회가 실패하면 정상 보고서로 오인되지 않도록 장애 보고서로 전환한다.

## 8. 집계 규칙

### 8.1 성공률 분모와 분자

- 분모는 선택된 등록 수집기 수다.
- 분자는 보고일에 귀속된 정기 실행의 최종 대표 상태가 `SUCCESS` 또는 `SUCCESS_EMPTY`인 수집기 수다.
- 수동·백필 실행은 이력에 보조 표시하지만 성공률에는 포함하지 않는다.
- 정기 실행이 없으면 `NOT_RUN`으로 집계한다.
- 조회 실패는 성공으로 집계하지 않는다.

### 8.2 수집기 대표 상태

수집기에 정기 실행 회차가 하나면 그 회차의 최종 결과를 사용한다. 재시도 등으로 같은 정기 회차의 기록이 여러 개면 가장 최근 완료 결과를 대표 상태로 선택한다. 실패 후 성공한 정기 재시도가 있으면 성공으로 집계하되 이전 실패 실행은 이력 표에 유지한다.

하루에 서로 다른 정기 회차가 여러 개인 수집기는 모든 회차가 성공 계열일 때만 성공 수집기로 계산한다. 하나라도 성공으로 회복되지 않은 실패 계열 회차가 있으면 해당 수집기를 실패로 강조한다.

대표 상태 우선순위는 다음과 같다.

1. `SOURCE_ERROR`(조회 실패)
2. `FAILED`, `PARTIAL_FAILED`, `ABORTED`
3. `RUNNING`
4. `NOT_RUN`
5. `WARNING`
6. `SUCCESS_EMPTY`
7. `SUCCESS`

`execution_kind`가 없는 기존 수집기의 실행은 기존 어댑터와 정책 서비스의 정기 실행 귀속 결과를 따른다. 보고 계층에서 날짜만으로 임의 재분류하지 않는다.

### 8.3 상태별 표시

- 정상: `SUCCESS`, `SUCCESS_EMPTY`
- 주의: `WARNING`, `RUNNING`
- 실패 강조: `FAILED`, `PARTIAL_FAILED`, `ABORTED`, `NOT_RUN`, `SOURCE_ERROR`

실행 중 상태가 전일 보고서에 남아 있으면 장기 실행 가능성을 알리기 위해 주의 영역에 표시한다. 상태를 감사 DB에 다시 기록하거나 보정하지 않는다.

## 9. 보고서 모델과 메일 형식

보고서 모델은 렌더러나 Gmail 구현에 의존하지 않으며 다음을 포함한다.

- 보고일과 KST 조회 범위
- 전체·성공 수집기 수와 상태별 수집기 수
- 조회 오류가 있는 수집기 목록
- 수집기별 대표 상태와 전체 실행 이력
- 생성 시각

메일 제목의 기본 형식은 다음과 같다.

```text
[수집 일일보고] 2026-09-17 - 4/5 수집기 성공
```

모든 데이터 소스 조회에 실패하면 다음 형식을 사용한다.

```text
[보고서 생성 오류] 2026-09-17 - 수집기 이력 조회 실패
```

HTML 본문은 다음 순서로 구성한다.

1. 전체 요약: 성공 수집기/전체 수집기, 상태별 건수
2. 주의 필요 수집기: 실패 강조 대상과 주의 대상
3. 수집기별 실행 이력: 표시명, 예정일·예정 시각, 시작·종료 시각, 실행 종류, 상태, 대상·성공·실패·처리 건수, 정제된 오류 범주

HTML을 표시하지 못하는 클라이언트를 위해 동일한 의미의 텍스트 본문을 `multipart/alternative`로 제공한다. 메일 내용에는 원문 예외, 원문 응답, URL, 파일 경로, 인증정보, DB 연결정보를 포함하지 않는다.

## 10. 중복 방지 상태

발송 완료 키는 보고일과 정렬된 수집기 ID 목록으로 구성한다. 수신자 변경만으로 자동 재발송하지 않으며 재발송은 `--force`로 명시한다.

상태 파일에는 다음 최소 정보만 기록한다.

- 발송 완료 키
- 발송 완료 UTC 시각
- Gmail 메시지 ID
- 보고서 성공 수집기 수와 전체 수집기 수

Gmail 전송 성공 응답을 받은 뒤 임시 파일을 같은 디렉터리에 쓰고 원자적으로 교체한다. 전송 실패, 조회 중단, 렌더링 실패 시 완료 상태를 기록하지 않는다. 상태 파일이 손상되면 안전하게 발송을 중단하고 운영자에게 복구 또는 `--force` 실행을 요구하여 예기치 않은 중복 메일을 막는다.

동시 실행으로 같은 보고서가 중복 전송되지 않도록 상태 파일과 같은 위치에 배타 잠금을 획득한다. 잠금을 획득하지 못하면 중복 실행으로 간주하여 전송하지 않고 비정상 종료한다.

## 11. 오류 처리와 종료 코드

| 상황 | 동작 | 종료 결과 |
| --- | --- | --- |
| 일부 수집기 조회 실패 | 조회 실패를 강조해 나머지 결과와 함께 전송 | 전송 성공 시 성공 |
| 모든 수집기 조회 실패 | 장애 제목과 장애 본문 전송 | 전송 성공 시 성공, 로그에 불완전 보고 명시 |
| Gmail 인증·전송 실패 | 상태 미기록, 정제된 오류 코드 기록 | 실패 |
| 이미 발송 완료 | 메일 미전송, 완료 키 기록 | 성공 |
| `--force` 재발송 성공 | 기존 완료 키의 최근 전송 정보 갱신 | 성공 |
| 상태 파일 손상 | 메일 미전송 | 실패 |
| 동시 실행 잠금 실패 | 메일 미전송 | 실패 |
| 잘못된 날짜·수집기·설정 | 실행 전 검증 실패 | 실패 |

로그에는 보고일, 대상 수집기 범위, 집계 결과, Gmail 메시지 ID 또는 고정된 오류 코드만 기록한다. 외부 라이브러리 예외 문자열은 그대로 로그에 남기지 않는다.

## 12. 테스트 전략

### 12.1 날짜와 조회

- 현재 시각에 따른 기본 전일 KST 계산
- KST 날짜 경계의 UTC 변환
- 선택 수집기 검증과 어댑터별 조회 격리
- 일부·전체 조회 실패

### 12.2 집계

- `4/5` 형태의 성공률 계산
- 성공, 성공·0건, 경고, 실행 중, 미실행, 실패 계열 대표 상태
- 실패 후 성공한 동일 정기 회차의 회복
- 서로 다른 복수 정기 회차 중 미회복 실패
- 수동·백필 실행의 이력 표시와 성공률 제외

### 12.3 렌더링과 보안

- 전체 요약, 수집기별 실행 이력, 실패 강조 HTML
- 동일 의미의 텍스트 본문
- HTML 이스케이프
- 비밀정보, 원문 오류, URL, 연결 문자열 미포함

### 12.4 Gmail과 상태

- `multipart/alternative` MIME과 To/Cc 헤더
- Gmail API 호출과 메시지 ID 처리
- 전송 성공 후에만 상태 기록
- 동일 키 중복 차단과 `--force` 재발송
- 원자적 상태 파일 교체, 손상 상태, 동시 실행 잠금
- 토큰 갱신과 최소 `gmail.send` 권한 범위

### 12.5 실행 경계와 회귀

- CLI 인자, 종료 코드, 로그 정제
- 배치 파일의 인자·종료 코드 전달 정적 검증
- 기존 모니터링 API와 어댑터 테스트

실제 Gmail 발송은 자동 테스트에서 수행하지 않는다. Gmail 클라이언트와 OAuth 자격 증명은 테스트 대역으로 교체하고, 운영 적용 전에 승인된 계정과 수신자를 사용한 감독된 1회 전송으로 확인한다.

## 13. 운영과 배포

1. 테스트 환경에서 전체 회귀 테스트를 통과시킨다.
2. Google Cloud Console에서 데스크톱 OAuth 클라이언트를 만들고 Gmail API를 활성화한다.
3. 발송 전용으로 사용할 개인 Gmail 계정으로 `authorize`를 한 번 실행한다.
4. 토큰 파일과 상태 파일을 저장소 밖의 접근 제한 경로에 배치한다.
5. `.env`에 Gmail 설정과 To/Cc 수신자를 등록한다.
6. 감독된 실행으로 보고 범위, 수신자, HTML·텍스트 본문, 실패 강조를 확인한다.
7. 배치 파일을 직접 실행해 종료 코드와 중복 차단을 확인한다.
8. Windows 작업 스케줄러에 매일 실행을 등록한다.
9. 다음 정기 발송 후 작업 스케줄러 이력, 애플리케이션 로그, Gmail 보낸편지함을 대조한다.

운영 문서는 최초 인증, 평상시 실행, 특정 보고일 재생성, 강제 재발송, 토큰 폐기·재발급, 상태 파일 손상, Gmail 장애, 작업 스케줄러 장애 대응 절차를 포함한다.

## 14. 완료 기준

- 기본 실행이 전일 KST의 등록 수집기 전체를 보고한다.
- 제목과 본문에서 `성공 수집기/전체 수집기`를 즉시 확인할 수 있다.
- 수집기별 실행 이력과 실패·미실행·조회 실패 강조가 제공된다.
- 수동·백필 이력은 표시되지만 정기 실행 성공률을 왜곡하지 않는다.
- 일부 조회 장애에서도 나머지 결과가 전달되고 전체 조회 장애가 정상 보고서로 보이지 않는다.
- 동일 보고일·동일 범위의 중복 발송이 차단되고 `--force`로만 재발송된다.
- Gmail 전송에 실패하면 완료 상태가 기록되지 않는다.
- 비밀정보와 원문 오류가 메일, 로그, 상태 파일에 노출되지 않는다.
- 감사·업무·제어 DB를 변경하지 않는다.
- 배치 파일을 Windows 작업 스케줄러에서 무인 실행할 수 있다.
- 신규 테스트와 기존 회귀 테스트가 모두 통과한다.
