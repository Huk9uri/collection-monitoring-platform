# 네이버 방문자·블로그 리뷰 수집 모니터링 설계

## 1. 목적

`C:\workspace\naver_crawling`의 네이버 방문자 리뷰와 블로그 리뷰 수집기에 실행 감사 이력을 추가하고, `collection-monitoring-platform`에서 두 수집기의 실행 상태·처리 결과·데이터 신선도를 독립적으로 조회한다.

대상 수집기는 다음과 같다.

| 수집기 ID | 표시명 | 업무 테이블 | 정기 실행 |
| --- | --- | --- | --- |
| `naver-review-visitor` | 네이버 방문자 리뷰 | `dbo.naver_review_visitor` | 매일 07:00 KST |
| `naver-review-blog` | 네이버 블로그 리뷰 | `dbo.naver_review_blog` | 매일 07:30 KST |

## 2. 범위

### 2.1 포함

- 두 리뷰 크롤러가 공유하는 실행 감사 모듈
- 공용 RUN·ATTEMPT 감사 테이블과 생성·검증 SQL
- 정기·수동·기간 지정·백필 실행의 구분
- 매장별 처리 결과와 정제된 오류 분류 기록
- FastAPI 공용 어댑터와 두 독립 수집기 등록
- 실행 목록·상세·KPI·미실행·장기 실행·신선도 조회
- 기존 모니터링 기준 일정 화면을 통한 정책 관리
- 수집기·API·웹 테스트와 운영 문서

### 2.2 제외

- 리뷰 원문, URL, 브라우저 HTML, 자유 형식 예외 메시지의 감사 저장
- 대시보드에서 수집기를 실행·중지·재실행하는 기능
- 기존 리뷰 업무 데이터의 수정 또는 마이그레이션
- 구현 과정에서의 운영 DB DDL 적용과 운영 서버 파일 교체
- 수동·기간 지정·백필 실행을 정기 실행 KPI에 포함하는 기능

## 3. 기본 원칙

- 수집기별 DB 차이는 FastAPI 어댑터 내부에서 처리한다.
- 웹은 `naverDB`의 감사·업무 테이블 구조를 알지 않는다.
- 감사 기록은 업무 데이터 커밋과 트랜잭션을 분리한다.
- 감사 실패 때문에 이미 성공한 업무 데이터 커밋을 되돌리지 않는다.
- 비밀정보, 리뷰 원문, 원문 오류를 저장하거나 공개 API에 노출하지 않는다.
- 정기 실행만 최신 상태, KPI, 미실행, 장기 실행, 신선도 판정에 사용한다.
- 정책 값은 웹에서 관리하지만 판정은 FastAPI가 단일 기준으로 수행한다.
- 구현은 테스트 우선으로 진행한다.

## 4. 전체 구조

```text
Windows 작업 스케줄러
├─ 방문자 리뷰 크롤러 ─┐
└─ 블로그 리뷰 크롤러 ─┼─> naverDB
                       │   ├─ 기존 리뷰 업무 테이블
                       │   ├─ NAVER_REVIEW_COLLECTION_RUN
                       │   └─ NAVER_REVIEW_COLLECTION_ATTEMPT
                       │
                       └─> FastAPI 리뷰 모니터링 어댑터
                            ├─ naver-review-visitor
                            └─ naver-review-blog
                                      │
                                      ▼
                              React 운영 대시보드
```

`naver_crawling`에는 두 리뷰 크롤러만 공유하는 `naver_review_monitoring.py`를 둔다. HMR과 FC다움은 각자의 저장소와 감사 구조를 계속 사용한다.

## 5. 감사 데이터 모델

### 5.1 `dbo.NAVER_REVIEW_COLLECTION_RUN`

| 컬럼 | 형식 | 규칙 |
| --- | --- | --- |
| `RunId` | `UNIQUEIDENTIFIER` | 기본키 |
| `ReviewKind` | `VARCHAR` | `visitor`, `blog` |
| `ExecutionKind` | `VARCHAR` | `scheduled`, `manual`, `backfill` |
| `TargetKind` | `VARCHAR` | `all-stores`, `single-store`, `date-range` |
| `ScheduledAt` | `DATETIME2` NULL | 정기 회차만 UTC 저장 |
| `StartedAt` | `DATETIME2` | UTC |
| `CompletedAt` | `DATETIME2` NULL | UTC |
| `Status` | `VARCHAR` | 허용 상태만 CHECK |
| `TargetStoreCount` | `INT` NULL | 확정된 대상 매장 수 |
| `SuccessfulStoreCount` | `INT` | 음수 금지 |
| `FailedStoreCount` | `INT` | 음수 금지 |
| `SourceCount` | `INT` NULL | 확인된 리뷰 수 합계 |
| `InsertedCount` | `INT` NULL | 커밋된 신규 적재 수 합계 |
| `TargetDateFrom` | `DATE` NULL | 기간 실행 시작일 |
| `TargetDateTo` | `DATE` NULL | 기간 실행 종료일 |
| `TargetPlaceId` | `VARCHAR` NULL | 단일 매장 실행 대상 |

정기 실행은 `(ReviewKind, ScheduledAt)` 고유 제약으로 같은 예정 회차의 중복 기록을 막는다. 수동·백필은 `ScheduledAt`을 `NULL`로 두고 매번 새 `RunId`를 생성한다.

대상 필드는 실행 형태와 일치해야 한다.

- `single-store`: `TargetPlaceId` 필수
- `date-range`: `TargetDateFrom`, `TargetDateTo` 필수, 시작일은 종료일 이하
- `all-stores`: 세 대상 필드 모두 `NULL`

### 5.2 `dbo.NAVER_REVIEW_COLLECTION_ATTEMPT`

| 컬럼 | 형식 | 규칙 |
| --- | --- | --- |
| `RunId` | `UNIQUEIDENTIFIER` | RUN 외래키 |
| `PlaceId` | `VARCHAR` | 매장 식별자 |
| `AttemptNo` | `INT` | 1 이상 |
| `BrandCode` | `VARCHAR` NULL | 매핑된 브랜드 코드 |
| `BrandName` | `NVARCHAR` | 정제된 표시명 |
| `StoreName` | `NVARCHAR` | 정제된 표시명 |
| `StartedAt` | `DATETIME2` | UTC |
| `CompletedAt` | `DATETIME2` NULL | UTC |
| `Status` | `VARCHAR` | 허용 상태만 CHECK |
| `SourceCount` | `INT` NULL | 확인된 리뷰 수 |
| `InsertedCount` | `INT` NULL | 커밋된 신규 적재 수 |
| `Committed` | `BIT` NULL | 업무 DB 반영 여부 |
| `ErrorCategory` | `VARCHAR` NULL | 허용 목록의 정제 코드 |

기본키는 `(RunId, PlaceId, AttemptNo)`로 구성한다. 자유 형식 오류, 리뷰 텍스트, 리뷰 URL, 브라우저 산출물은 저장하지 않는다.

## 6. 실행 종류 판정

| 조건 | `ExecutionKind` | `TargetKind` |
| --- | --- | --- |
| 작업 스케줄러의 기본 전체 실행 | `scheduled` | `all-stores` |
| `--place-id` | `manual` | `single-store` |
| 날짜 범위를 지정한 전체 실행 | `manual` | `date-range` |
| `--backfill` | `backfill` | 대상 인수에 따라 결정 |
| `--dry-run` | 감사 미기록 | 해당 없음 |

정기 실행 여부를 단순히 인수 부재만으로 추정하지 않는다. 작업 스케줄러 BAT가 `--scheduled` 인수를 전달하고 크롤러는 이 인수가 `--place-id`, `--backfill`, 날짜 범위와 함께 사용되지 않도록 검증한다. 사용자가 직접 기본 인수 없이 실행한 경우는 `manual`·`all-stores`로 기록한다.

## 7. 크롤러 기록 흐름

1. CLI 인수를 검증하고 실행 종류·대상 범위를 확정한다.
2. DB 쓰기 실행이면 RUN을 `RUNNING`으로 생성한다.
3. 매장 처리 직전에 ATTEMPT를 시작한다.
4. 수집과 기존 업무 테이블 커밋을 완료한다.
5. 업무 커밋 결과를 근거로 ATTEMPT의 건수·상태·`Committed`를 확정한다.
6. 재시도 시 같은 `PlaceId`에 증가한 `AttemptNo`를 기록한다.
7. 모든 매장 처리 후 최종 ATTEMPT만 집계해 RUN을 종료한다.
8. 처리 루프 밖 예외도 가능한 범위에서 RUN을 `FAILED` 또는 `ABORTED`로 종료한 뒤 다시 전파한다.

감사 저장은 짧은 별도 연결과 트랜잭션을 사용한다. 감사 기록 실패는 운영 로그와 비정상 종료 코드로 드러내되, 이미 커밋된 리뷰 업무 데이터를 롤백하지 않는다.

## 8. 상태 판정

### 8.1 저장 상태

| 조건 | RUN 상태 |
| --- | --- |
| 실행 중 | `RUNNING` |
| 모든 최종 시도 성공, 신규 적재 있음 | `SUCCESS` |
| 모든 최종 시도 성공, 신규 적재 없음 | `SUCCESS_EMPTY` |
| 성공 매장과 최종 실패 매장이 함께 존재 | `PARTIAL_FAILED` |
| 성공 매장 없이 최종 실패 | `FAILED` |
| 프로세스가 명시적으로 중단됨 | `ABORTED` |

매장별 오류 분류는 다음 고정 목록만 허용한다.

- `CAPTCHA_DETECTED`
- `PAGE_LOAD_FAILED`
- `PARSE_FAILED`
- `DB_WRITE_FAILED`
- `BRAND_MAPPING_FAILED`
- `UNEXPECTED_ERROR`

리뷰 없음과 수집 대상 기간에 해당 리뷰가 없음은 실패가 아니라 성공·0건으로 기록한다. 새 분류가 필요하면 DDL 허용 목록, 수집기 매핑, API 스키마와 테스트를 함께 변경한다.

### 8.2 조회 시 정책 상태

FastAPI는 제어 DB 정책과 정기 실행 이력을 결합한다.

- 예정 시각 + 시작 유예 이후 해당 정기 RUN이 없으면 `NOT_RUN`
- `RUNNING`이 최대 실행시간을 넘으면 조회 결과만 `ABORTED`
- 수동·백필 실행은 위 판정과 최신 정기 상태 선택에서 제외
- 조회 시 합성 상태는 감사 원본과 과거 실행 상세를 변경하지 않음
- 정책이 없거나 비활성화되면 저장 상태만 사용

## 9. 정책 관리

초기 정책은 제어 DB에 등록하고 기존 `모니터링 기준 일정` 화면에서 수정한다.

| 수집기 | 시간대 | 일정 | 시작 유예 | 최대 실행 | 귀속 범위 |
| --- | --- | --- | ---: | ---: | ---: |
| 방문자 리뷰 | `Asia/Seoul` | 매일 07:00 | 30분 | 360분 | 360분 |
| 블로그 리뷰 | `Asia/Seoul` | 매일 07:30 | 30분 | 360분 | 360분 |

프론트엔드는 설정 입력·조회·변경 검토를 담당한다. API는 정책 검증, 낙관적 버전 충돌 처리, 변경 이력 저장과 상태 판정을 담당한다. 정책 변경은 다음 조회부터 적용한다.

## 10. FastAPI 어댑터

공용 어댑터 구현은 `ReviewKind`를 생성자 인수로 받아 다음 두 인스턴스를 등록한다.

- `naver-review-visitor`: `ReviewKind='visitor'`
- `naver-review-blog`: `ReviewKind='blog'`

어댑터는 기존 `CollectorAdapter` 계약을 구현한다.

- `latest`: 최신 정기 실행
- `list_runs`: 정기·수동·백필 전체 실행 이력
- `count_runs`, `count_runs_by_status`
- `get_run`: 매장별 ATTEMPT 포함
- `latest_successful_check_at`: 최신 성공 정기 실행의 완료 시각
- `freshness`: 업무 테이블의 실제 최신 리뷰 시각
- `readiness`: 필요한 감사·업무 테이블 SELECT 가능 여부

한 인스턴스의 조회 실패는 공통 부분 장애 응답으로 격리하며 다른 수집기 결과를 가리지 않는다.

## 11. 공개 API와 웹 표시

기존 모니터링 API 엔드포인트와 공통 응답 모델을 유지한다. 웹에는 수집기별 별도 카드와 실행 이력 필터 항목을 추가한다.

실행 목록에는 수집기, 실행 종류, 상태, 시작 시각, 대상·성공·실패 매장 수, 확인 리뷰 수와 신규 적재 수를 표시한다. 상세 드롭다운에는 매장별 최종·재시도 결과와 정제된 오류 분류를 표시한다.

정기 실행만 KPI와 수집기 카드 최신 상태에 반영한다. 수동·기간 지정·백필은 실행 이력과 상세에서만 확인한다.

## 12. 신선도

각 리뷰 수집기는 업무 테이블에서 실제 최신 리뷰 시각을 읽어 하나의 고정 데이터셋을 제공한다.

- 방문자 리뷰: `visitor-reviews`
- 블로그 리뷰: `blog-reviews`

`last_successful_check_at`은 최신 성공 정기 실행의 완료 시각이고, `latest_data_at`은 업무 테이블의 실제 최신 리뷰 시각이다. 신규 리뷰가 없는 정상 실행도 성공 확인 시각은 갱신하되 실제 데이터 시각은 유지한다. 신선도 SLA는 기존 설정 화면에서 선택적으로 관리한다.

## 13. 테스트 전략

### 13.1 `naver_crawling`

- RUN·ATTEMPT 시작, 성공 종료, 실패 종료
- 감사 쓰기와 업무 데이터 커밋의 트랜잭션 분리
- 방문자·블로그의 정상, 빈 결과, 부분 실패, 전체 실패
- 정기·수동·단일 매장·기간 지정·백필·dry-run 분류
- 재시도 최종 시도 집계
- 허용되지 않은 오류 문자열과 원문 데이터 저장 거부
- 감사 실패 시 기존 업무 커밋 비롤백
- 생성·검증 SQL의 제약조건·인덱스·권한 계약

### 13.2 모니터링 API

- 공용 테이블의 `ReviewKind` 격리
- 목록·상세·카운트·신선도·readiness
- 최신 상태가 정기 실행만 선택하는지 검증
- 수동 성공이 정기 실패·미실행을 덮지 않는지 검증
- `NOT_RUN`, stale `ABORTED`, 정책 비활성화
- 두 리뷰 수집기와 기존 수집기의 부분 장애 격리
- 비밀정보와 원문 오류 비노출

### 13.3 웹

- 두 수집기 카드와 표시명
- 최신 정기 상태 KPI 집계
- 실행 종류와 매장별 상세 드롭다운
- 설정 화면의 두 수집기 정책 조회·수정
- 읽기 전용 사용자의 설정 조회와 관리자 저장 권한

## 14. 배포 순서

1. 수집기와 모니터링 플랫폼의 테스트를 모두 통과시킨다.
2. 운영 권한이 있는 담당자가 감사 DDL과 검증 SQL을 적용한다.
3. 모니터링 API에 신규 어댑터를 배포하되 정책 판정은 비활성 상태로 둔다.
4. 서버의 방문자·블로그 크롤러와 BAT를 교체한다.
5. 감독된 수동 검증으로 RUN·ATTEMPT와 업무 적재 결과를 대조한다.
6. 제어 DB에 07:00/07:30 정책을 저장하고 일정 기반 판정을 활성화한다.
7. 다음 정기 실행 후 카드·목록·상세·신선도·부분 장애를 확인한다.

운영 DB 적용, 서버 파일 교체, 작업 스케줄러 변경은 별도 승인 없이는 수행하지 않는다.

## 15. 완료 기준

- 두 리뷰 수집기가 DB 쓰기 실행마다 안전한 감사 이력을 남긴다.
- 대시보드에 방문자·블로그 리뷰가 독립 수집기로 표시된다.
- 정기 실행만 최신 상태·KPI·미실행·장기 실행 판정에 사용된다.
