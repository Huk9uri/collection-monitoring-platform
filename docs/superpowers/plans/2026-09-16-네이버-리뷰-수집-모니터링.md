# 네이버 방문자·블로그 리뷰 수집 모니터링 구현 계획

> **에이전트 작업자 필수 하위 스킬:** 이 계획을 작업별로 구현할 때 `superpowers:subagent-driven-development`(권장) 또는 `superpowers:executing-plans`를 사용한다. 모든 단계는 체크박스(`- [ ]`)로 추적한다.

**목표:** 네이버 방문자·블로그 리뷰 크롤러가 안전한 공용 감사 이력을 남기고, 모니터링 플랫폼이 두 수집기를 독립적으로 조회·판정·표시하도록 구현한다.

**아키텍처:** `naver_crawling`에 공용 RUN/ATTEMPT 스키마와 `naver_review_monitoring.py`를 추가해 두 크롤러가 공유한다. `collection-monitoring-platform`은 `ReviewKind`로 격리된 공용 어댑터 두 개를 등록하고, 제어 DB 정책을 적용해 정기 실행만 최신 상태와 KPI에 반영한다.

**기술 스택:** Python 3.12, pymssql, SQL Server, FastAPI, Pydantic, pytest/unittest, React 19, TypeScript, TanStack Query, Vitest

**설계:** `docs/superpowers/specs/2026-09-16-네이버-리뷰-수집-모니터링-설계.md`

## 전역 제약

- 설계·구현·운영 문서는 한국어로 작성한다.
- 업무 테이블은 `dbo.naver_review_visitor`, `dbo.naver_review_blog`를 유지한다.
- 감사 테이블에는 비밀정보, 리뷰 원문, URL, HTML, 자유 형식 오류를 저장하지 않는다.
- 감사 트랜잭션은 업무 적재 트랜잭션과 분리하며 이미 커밋된 업무 데이터를 되돌리지 않는다.
- 정기 실행만 최신 상태, KPI, `NOT_RUN`, stale `ABORTED`, 신선도 판정에 사용한다.
- 수동·기간 지정·백필은 실행 이력과 상세에만 포함하고 `--dry-run`은 감사 기록을 남기지 않는다.
- 운영 DB DDL 적용, 서버 파일 교체, 작업 스케줄러 변경은 수행하지 않는다.
- 실행 시작 전 두 저장소에 각각 격리 브랜치 또는 worktree를 만든다. `naver_crawling` 쓰기 권한이 없으면 권한을 요청하고 우회 복사본을 만들지 않는다.
