# 데이터 수집 모니터링 플랫폼 설계

작성일: 2026-09-08

## 1. 목적

FC다움과 HMR을 시작으로 블로그, 리뷰, 네이버 영업시간 등 여러 데이터
수집기의 실행 상태와 DB 적재 결과를 하나의 운영 화면에서 확인한다.

MVP는 읽기 전용이다. API 호출 성공 여부, DB 커밋 결과, 데이터 신선도를
구분하여 신규 데이터가 없는 정상 실행을 장애로 오판하지 않는다.

## 2. 저장소와 시스템 경계

이 프로젝트는 `Huk9uri/collection-monitoring-platform` 독립 private 저장소로
운영한다. 기존 `dashboard-design-system` 전체를 복제하지 않고 모니터링에
필요한 디자인 토큰과 UI 패턴만 선별 적용한다.

기존 수집기 저장소는 다음 책임을 가진다.

- 외부 API 호출과 데이터 변환
- 업무 테이블 적재
- 실행 및 작업별 감사 이력 기록

모니터링 플랫폼은 다음 책임을 가진다.

- 감사 이력과 업무 테이블 읽기
- 수집기별 상태를 공통 모델로 변환
- 전체 및 수집기별 상태 집계
- 읽기 전용 API와 운영 화면 제공

## 3. 프로젝트 구조

```text
collection-monitoring-platform/
├─ apps/
│  ├─ web/                 # React 19, TypeScript, Vite
│  └─ api/                 # Python 3.12, FastAPI
├─ docs/
│  ├─ 설계/
│  ├─ 구현계획/
│  └─ 운영/
├─ AGENTS.md
├─ .env.example
└─ README.md
```

웹과 API는 하나의 저장소에서 계약과 변경 이력을 공유하지만 서로 다른
프로세스로 실행하고 독립적으로 배포할 수 있다.

## 4. 백엔드 아키텍처

FastAPI 서비스는 API 라우터, 애플리케이션 서비스, 수집기 어댑터, 읽기 전용
저장소, 설정으로 나눈다.

초기 어댑터는 다음과 같다.

- `fcdaum`: FC다움 실행/브랜드 감사 이력과 리포트·문제항목·미션 신선도 조회
- `hmr`: HMR 실행/채널 감사 이력과 주문 데이터 신선도 조회

향후 블로그, 리뷰, 네이버 영업시간 수집기는 같은 어댑터 계약을 구현한다. 한
어댑터의 DB 장애가 다른 수집기의 정상 결과를 가리지 않도록 부분 응답을
허용한다.

## 5. 공통 상태

| API 상태 | 화면 표시 | 판정 |
| --- | --- | --- |
| `SUCCESS` | 정상 | 모든 작업이 최종 성공하고 신선도가 정상이다. |
| `SUCCESS_EMPTY` | 데이터 없음 | 호출과 커밋은 성공했지만 원천 데이터가 0건이다. |
| `WARNING` | 주의 | 최종 성공했지만 재시도 또는 신선도 지연이 있다. |
| `PARTIAL_FAILED` | 부분 실패 | 일부 작업은 성공하고 일부 작업은 최종 실패했다. |
| `FAILED` | 실패 | 모든 작업이 실패했거나 실행 초기화가 실패했다. |
| `RUNNING` | 실행 중 | 허용시간 안에서 실행 중이다. |
| `ABORTED` | 중단 | 허용시간 초과 또는 비정상 종료 상태다. |
| `NOT_RUN` | 미실행 | 예정 시각 이후 실행 이력이 없다. |

`PARTIAL_FAILED`는 `WARNING`이 아닌 장애 등급이며 전체 실패 건수에 포함한다.
실행 상태는 작업별 마지막 시도로 계산한다. 실패 후 재시도 성공은
`WARNING`이다.

## 6. 감사 이력

HMR은 기존 `CHANNEL_COLLECTION_RUN`과 `CHANNEL_COLLECTION_ATTEMPT`를
사용한다. FC다움에는 `FC_DAUM_COLLECTION_RUN`과
`FC_DAUM_COLLECTION_ATTEMPT`를 추가한다.

감사 이력은 실행 ID, 예정일, 시작·종료 시각, 작업명, 시도 번호, 상태, API
건수, 신규·변경·동일 건수, DB 커밋 여부, 정규화된 오류 분류를 저장한다.
계정, 비밀번호, 쿠키, 토큰, 응답 본문, 업무 데이터, 원문 예외는 저장하지
않는다.

## 7. 읽기 API

- `GET /api/v1/monitoring/summary`
- `GET /api/v1/monitoring/collectors`
- `GET /api/v1/monitoring/runs`
- `GET /api/v1/monitoring/runs/{collector_id}/{run_id}`
- `GET /api/v1/monitoring/freshness`
- `GET /health/live`
- `GET /health/ready`

이력 조회에는 최대 기간과 페이지 크기를 적용한다. 테이블명과 DB 연결명은
사용자 입력으로 받지 않는다. API 시각은 UTC ISO 8601로 반환하며 웹에서
Asia/Seoul 시각으로 표시한다.

## 8. 화면

모니터링 전용 화면만 제공한다.

- 전체 상태와 오늘의 성공·장애 건수
- 수집기별 최신 상태 카드와 브랜드/채널 요약
- 원천 및 적재 데이터 신선도
- 필터와 페이지네이션을 제공하는 실행 이력
- 시도, 재시도, 적재 결과를 표시하는 실행 상세 패널
- 로딩, 빈 결과, 일부 데이터 소스 장애, 전체 오류 상태
- 사용자 수동 새로고침

수집 실행이나 삭제 버튼은 제공하지 않는다.

## 9. 인증과 향후 쓰기 기능

MVP에서는 로그인을 구현하지 않는다. 사내망 배포, 명시적 CORS Origin,
데이터 소스별 읽기 전용 DB 계정으로 접근을 제한한다.

FastAPI에는 `CurrentUser`와 역할 검사 경계를 두고 익명 `viewer`를 기본으로
사용한다. 예약 역할은 `viewer`, `operator`, `admin`이다. 향후 OIDC, 사내
SSO 또는 JWT 인증으로 교체할 수 있어야 한다.

향후 쓰기 액션은 조회 계정과 분리된 DB 계정 및 서비스 계층을 사용하고 사용자,
시각, 대상, 요청 식별자, 결과를 별도 감사 이력에 남긴다.

## 10. 검증

- FC다움 감사 이력의 성공, 재시도, 부분 실패, 전체 실패, 롤백 테스트
- FC다움/HMR 어댑터의 공통 모델 변환 테스트
- `WARNING`, `PARTIAL_FAILED`, `FAILED` 경계 테스트
- 한 DB 장애 시 다른 수집기 결과를 유지하는 테스트
- FastAPI 스키마, 페이지네이션, 준비 상태 테스트
- React 로딩, 오류, 필터, 상세 패널과 한국 시각 표시 테스트
- Python 테스트, TypeScript 테스트, 린트, 프로덕션 빌드

실제 DB 검증은 읽기 전용 스모크 테스트로 제한하며 수집 작업은 실행하지 않는다.
