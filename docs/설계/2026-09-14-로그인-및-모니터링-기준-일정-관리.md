# 모니터링 로그인 및 기준 일정 관리 설계

## 1. 목적

데이터 수집 모니터링 대시보드의 조회 화면을 인터넷에 공개하지 않고, 로그인한
사용자만 수집 현황을 조회하도록 변경한다. 관리자는 대시보드에서 수집기별
모니터링 기준 요일·시각·시간대와 상태 판정 임계치를 수정할 수 있어야 한다.

이 설정은 대시보드의 `미실행`, `지연`, `신선도 초과` 판정에만 사용한다.
Windows 작업 스케줄러와 실제 수집기 실행 일정은 조회하거나 변경하지 않는다.

## 2. 범위

### 2-1. 포함

- 대시보드 자체 아이디·비밀번호 로그인
- 기존 `viewer`, `admin` 역할
- 로그인 사용자만 모니터링 조회
- 관리자만 모니터링 기준 일정과 판정 임계치 수정
- 일정 변경 전후 값, 변경자, 변경 사유 감사
- DB 정책 우선, `.env` 정책 fallback
- 기존 FC다움, HMR 및 이후 추가되는 수집기에 공통 적용
- 일일·주간·복수 요일·하루 복수 시각 표현

### 2-2. 제외

- Windows 작업 스케줄러 변경
- 수집기 실행·재실행·중단
- 수집 업무 테이블 INSERT·UPDATE·DELETE
- 공개 회원가입
- 이메일 비밀번호 찾기
- 소셜 로그인과 사내 SSO
- 사용자 관리 화면

초기 사용자 생성과 비밀번호 초기화는 서버 CLI로 수행한다.

## 3. 권한 모델

| 상태 | 로그인 | 모니터링 조회 | 기준 일정 조회 | 기준 일정 수정 | 변경 이력 조회 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 비로그인 | 가능 | 불가 | 불가 | 불가 | 불가 |
| `viewer` | 완료 | 가능 | 가능 | 불가 | 불가 |
| `admin` | 완료 | 가능 | 가능 | 가능 | 가능 |

화면에서 관리자 메뉴를 숨기는 것은 편의 기능이다. 실제 권한은 모든 API 요청에서
FastAPI가 다시 검사한다. 인증되지 않은 요청은 `401`, 역할이 부족한 요청은
`403`을 반환한다.

## 4. 인증 설계

### 4-1. 사용자와 비밀번호

- 사용자 아이디는 대소문자를 구분하지 않는 고유 값으로 관리한다.
- 비밀번호는 Argon2id 해시로만 저장한다.
- 평문 비밀번호와 복호화 가능한 비밀번호는 DB·로그·환경변수에 저장하지 않는다.
- 공개 회원가입은 제공하지 않는다.
- 초기 관리자와 viewer는 서버 CLI에서 대화형으로 생성한다.
- 비활성화된 사용자는 기존 세션을 포함해 즉시 접근할 수 없어야 한다.

### 4-2. 서버 세션

- 로그인 성공 시 256비트 이상의 난수로 세션 토큰을 생성한다.
- DB에는 세션 토큰 원문 대신 SHA-256 해시를 저장한다.
- 브라우저에는 `HttpOnly`, `Secure`, `SameSite=Lax` 쿠키로 원문 토큰을
  전달한다.
- 세션은 마지막 사용 후 8시간에 만료하고, 생성 후 최대 24시간을 넘지 않는다.
- `last_seen_at`은 매 요청마다 쓰지 않고 마지막 갱신 후 5분이 지난 인증 요청에서만
  갱신한다.
- 로그아웃, 사용자 비활성화, 비밀번호 변경 시 관련 세션을 폐기한다.
- 인증 성공 후 로그인 이전의 앱 내부 경로로 복귀할 수 있다.
- 복귀 경로는 `/`로 시작하는 상대 경로만 허용해 외부 리다이렉트를 차단한다.

JWT를 브라우저 `localStorage`에 저장하지 않는다. 서버 세션을 사용해 로그아웃,
권한 회수와 강제 만료를 서버에서 통제한다.

### 4-3. 로그인 보호

- 계정과 요청 IP를 조합해 연속 로그인 실패를 제한한다.
- 실패 횟수와 잠금 여부로 사용자 존재를 추측할 수 없도록 동일한 오류 문구를 쓴다.
- 비밀번호와 세션 토큰을 애플리케이션·프록시 로그에 남기지 않는다.
- 로그인 성공과 실패, 로그아웃, 비밀번호 변경을 보안 감사 이벤트로 기록한다.

## 5. CSRF와 웹 보안

- 상태 변경 요청은 세션 쿠키와 별도의 CSRF 토큰을 함께 검증한다.
- CSRF 토큰은 로그인 세션에 귀속하고 `X-CSRF-Token` 헤더로 전달한다.
- 로그인 성공 응답은 CSRF 토큰 원문을 한 번 반환한다. 브라우저 새로고침 후에는
  인증된 `GET /api/v1/auth/csrf`로 현재 세션의 CSRF 토큰을 재발급하고 이전
  토큰을 폐기한다. 원문은 브라우저 메모리에만 둔다.
- `Origin`과 `Host`도 운영 설정과 일치하는지 검사한다.
- CORS는 운영 웹 Origin 하나 또는 명시된 허용 목록만 사용한다.
- 운영 환경은 HTTPS만 허용하고 HTTP는 HTTPS로 리다이렉트한다.
- FastAPI `/docs`, `/redoc`, `/openapi.json`은 운영 환경에서 비활성화한다.
- `/health/live`만 비로그인 접근을 허용한다.
- DB 상태와 소스 구성을 노출하는 `/health/ready`는 인증된 관리자 또는
  로컬 헬스체크에서만 접근한다.

## 6. 데이터 모델

인증·설정 테이블은 수집 업무 테이블과 논리적으로 분리한다. 기존 SELECT 전용
연결은 유지하고, 인증·설정 전용 DB 계정에 아래 테이블의 필요한 권한만 부여한다.

### 6-1. `monitoring_user`

| 컬럼 | 형식 | 설명 |
| --- | --- | --- |
| `user_id` | `UNIQUEIDENTIFIER` | 사용자 식별자 |
| `username` | `NVARCHAR(100)` | 정규화된 고유 아이디 |
| `password_hash` | `NVARCHAR(500)` | Argon2id 해시 |
| `role` | `VARCHAR(30)` | `viewer` 또는 `admin` |
| `is_active` | `BIT` | 계정 활성 여부 |
| `password_changed_at` | `DATETIME2` | 비밀번호 변경 시각 |
| `created_at` | `DATETIME2` | 생성 시각 |
| `updated_at` | `DATETIME2` | 수정 시각 |
| `version` | `ROWVERSION` | 동시 수정 제어 |

### 6-2. `monitoring_session`

| 컬럼 | 형식 | 설명 |
| --- | --- | --- |
| `session_id` | `UNIQUEIDENTIFIER` | 세션 식별자 |
| `user_id` | `UNIQUEIDENTIFIER` | 사용자 |
| `token_hash` | `BINARY(32)` | 세션 토큰 SHA-256 |
| `csrf_token_hash` | `BINARY(32)` | CSRF 토큰 SHA-256 |
| `idle_expires_at` | `DATETIME2` | 유휴 만료 |
| `absolute_expires_at` | `DATETIME2` | 절대 만료 |
| `last_seen_at` | `DATETIME2` | 마지막 사용 |
| `revoked_at` | `DATETIME2 NULL` | 폐기 시각 |
| `created_at` | `DATETIME2` | 생성 시각 |

만료·폐기 세션 정리는 로그인 또는 인증 요청 시 제한된 건수로 수행하고, 이후
별도 운영 정리 작업으로 확장할 수 있다.

### 6-3. `monitoring_collector_policy`

| 컬럼 | 형식 | 설명 |
| --- | --- | --- |
| `collector_id` | `VARCHAR(50)` | 등록된 수집기 고유 ID |
| `timezone_name` | `VARCHAR(100)` | IANA timezone |
| `max_duration_minutes` | `INT NULL` | 장기 실행 중단 판정 기준 |
| `start_grace_minutes` | `INT` | 예정 시각 이후 미실행 판정 유예 |
| `schedule_attribution_window_minutes` | `INT` | 실제 실행을 예정 회차에 귀속할 범위 |
| `monitoring_enabled` | `BIT` | 일정 기반 판정 사용 여부 |
| `updated_at` | `DATETIME2` | 수정 시각 |
| `updated_by` | `UNIQUEIDENTIFIER` | 수정 관리자 |
| `version` | `ROWVERSION` | 낙관적 동시성 제어 |

수집기별 데이터셋 신선도 기준은
`monitoring_collector_freshness_policy(collector_id, dataset_id,
freshness_sla_minutes)`로 분리한다. 허용되는 `dataset_id`는 등록된 수집기
어댑터가 제공하는 고정 목록으로 검증한다.

### 6-4. `monitoring_collector_schedule`

| 컬럼 | 형식 | 설명 |
| --- | --- | --- |
| `schedule_id` | `UNIQUEIDENTIFIER` | 일정 식별자 |
| `collector_id` | `VARCHAR(50)` | 수집기 ID |
| `weekday_number` | `TINYINT` | 월요일 1 ~ 일요일 7 |
| `scheduled_time` | `TIME(0)` | 정책 timezone 기준 현지 시각 |
| `schedule_enabled` | `BIT` | 해당 일정 활성 여부 |

`collector_id + weekday_number + scheduled_time`에 고유 제약을 둔다. 한 수집기에
여러 요일과 여러 시각을 저장할 수 있으므로 일일, 평일, 특정 요일, 하루 복수 실행을
같은 모델로 표현한다.

### 6-5. 감사 테이블

`monitoring_policy_history`에는 다음을 저장한다.

- 변경 식별자와 수집기 ID
- 변경 관리자 ID
- 필수 변경 사유
- 변경 전후 정책 snapshot
- 변경 시각과 요청 추적 ID

snapshot은 비밀정보를 포함하지 않는 JSON으로 저장한다. UPDATE와 감사 INSERT는
하나의 DB 트랜잭션으로 처리한다. 인증 이벤트는 별도
`monitoring_auth_audit`에 결과 코드 중심으로 저장하며 비밀번호와 토큰은 저장하지
않는다.

## 7. 정책 조회와 fallback

정책 우선순위는 다음과 같다.

1. DB의 활성 정책과 활성 일정
2. 해당 수집기의 기존 `.env` 정책
3. 둘 다 없으면 일정 기반 상태 판정을 생략하고 저장된 실행 상태만 표시

DB에 유효한 정책이 하나라도 존재하면 해당 수집기에 대해 DB가 완전한 기준이다.
DB 값과 `.env` 값을 필드별로 섞지 않는다. 이는 일부 필드만 오래된 값으로
남는 상황을 방지한다.

API 프로세스는 최근 정상 정책 snapshot을 메모리에 최대 60초 캐시한다. 관리자가
정책을 저장하면 현재 프로세스의 캐시를 즉시 무효화한다. 다중 프로세스에서는
60초 이내 자연 갱신을 허용하며, 이후 필요할 때 DB 기반 버전 확인 또는 외부 캐시로
확장한다.

DB 조회 실패 시 메모리에 마지막 정상 snapshot이 있으면 그 값과
`policy_source=cached`를 사용하고 경고를 표시한다. snapshot이 없으면 `.env`
fallback을 사용한다. DB에 정책이 없다는 정상 결과와 DB 장애를 구분한다.

## 8. 상태 판정

각 수집기의 활성 일정 중 현재 시각 이전의 가장 최근 예정 회차를 계산한다.
예정 회차와 실행 이력을 비교해 다음을 판정한다.

- 예정 시각과 유예시간 이전: 미실행으로 판정하지 않음
- 유예시간 경과 후 해당 회차 실행 없음: `NOT_RUN`
- 실행 중이며 최대 실행시간 이내: `RUNNING`
- 최대 실행시간 초과: `ABORTED`
- 실행 완료: 저장된 canonical 상태 사용
- 신선도 SLA 초과: 성공 실행이어도 `WARNING`

요일과 시각 계산은 정책의 IANA timezone에서 수행한 뒤 UTC로 변환한다.
같은 날짜에 여러 회차가 있으면 각 실행을
`schedule_attribution_window_minutes` 범위의 가장 가까운 이전 회차에 귀속한다.

설정 변경은 저장 이후 생성되는 판정 snapshot부터 적용한다. 과거 실행 이력의
저장 상태를 다시 쓰지 않는다. 화면에는 현재 정책으로 계산한 상태임을 표시하고,
정책 변경 시각을 함께 제공한다.

## 9. API

### 9-1. 인증

| 메서드 | 경로 | 권한 | 설명 |
| --- | --- | --- | --- |
| `POST` | `/api/v1/auth/login` | 공개 | 로그인과 세션 발급 |
| `POST` | `/api/v1/auth/logout` | 로그인 | 현재 세션 폐기 |
| `GET` | `/api/v1/auth/me` | 로그인 | 사용자와 역할 조회 |
| `GET` | `/api/v1/auth/csrf` | 로그인 | CSRF 토큰 재발급 |
| `POST` | `/api/v1/auth/change-password` | 로그인 | 본인 비밀번호 변경 |

### 9-2. 모니터링 정책

| 메서드 | 경로 | 권한 | 설명 |
| --- | --- | --- | --- |
| `GET` | `/api/v1/settings/schedules` | viewer 이상 | 전체 기준 일정 조회 |
| `GET` | `/api/v1/settings/schedules/{collector_id}` | viewer 이상 | 수집기 정책 조회 |
| `PUT` | `/api/v1/settings/schedules/{collector_id}` | 관리자 | 정책 전체 교체 |
| `GET` | `/api/v1/settings/history` | 관리자 | 변경 이력 조회 |

`PUT`은 정책, 일정, 신선도 목록과 현재 `version`, 변경 사유를 받는다. 일부 필드
PATCH 대신 전체 정책 교체를 사용해 저장 결과를 명확히 한다. version이 현재 DB와
다르면 `409 CONFLICT`와 최신 정책을 반환한다.

FastAPI는 다음을 검증한다.

- 등록된 `collector_id`
- 유효한 IANA timezone
- 요일 1~7과 중복되지 않은 시각
- 양수인 실행시간·유예·신선도 기준
- 수집기별 허용 데이터셋 ID
- 비어 있지 않은 변경 사유
- 최소 한 개 이상의 활성 일정 또는 명시적인 일정 모니터링 비활성화

## 10. 웹 화면

### 10-1. 로그인

비로그인 사용자는 모든 앱 경로에서 로그인 화면으로 이동한다. 로그인 성공 후 원래
앱 내부 경로로 돌아간다. 세션 만료로 API가 `401`을 반환하면 현재 경로를 보존한
채 로그인 화면으로 이동한다.

### 10-2. 모니터링 기준 일정

viewer에게는 읽기 전용 정책을 표시한다. 관리자에게는 다음 편집 기능을 제공한다.

- 수집기 선택
- 시간대
- 실행 요일과 실행 시각 행 추가·삭제
- 최대 실행시간과 시작 유예
- 예정 회차 귀속 범위
- 데이터셋별 신선도 SLA
- 일정 기반 판정 활성화
- 필수 변경 사유

화면 제목은 `모니터링 기준 일정`으로 한다. 다음 안내를 항상 표시한다.

> 이 설정은 대시보드의 상태 판정 기준만 변경하며 실제 수집기 실행 일정에는
> 영향을 주지 않습니다.

저장 전 확인 대화상자에서 실제 수집 일정과 동일한지 다시 확인한다. 저장 충돌
`409`가 발생하면 사용자의 입력을 덮어쓰지 않고 최신 설정을 비교해 다시
편집하도록 안내한다.

## 11. DB 권한과 연결 분리

기존 FC다움·HMR·향후 수집기 연결은 계속 `ApplicationIntent=ReadOnly`와 SELECT
전용 계정을 사용한다.

인증·설정용 연결 문자열은 별도 환경변수
`MONITORING_CONTROL_CONNECTION_STRING`으로 주입한다. 해당 DB 계정은
모니터링 인증·설정·감사 테이블과 승인된 저장 프로시저에만 필요한 최소 권한을
갖는다. 수집 업무 테이블에는 쓰기 권한을 주지 않는다.

스키마 생성은 DBA 또는 승인된 마이그레이션 계정으로만 수행한다. 웹 요청 계정에는
CREATE, ALTER, DROP 권한을 주지 않는다.

## 12. 장애 처리

- 인증 DB 장애: 기존 세션도 안전하게 검증할 수 없으므로 로그인과 보호 API를
  `503`으로 차단한다.
- 정책 DB 장애: 마지막 정상 캐시 또는 `.env` fallback으로 조회를 계속하고
  설정 화면에 경고한다. 수정 요청은 `503`으로 실패하며 성공처럼 표시하지 않는다.
- 감사 INSERT 실패: 정책 UPDATE도 같은 트랜잭션에서 rollback한다.
- 세션 만료: `401` 반환 후 로그인 화면으로 이동한다.
- 역할 부족: `403`을 반환하고 관리자 기능을 실행하지 않는다.
- 동시 수정: `409`를 반환하고 최신 정책과 비교하도록 한다.

## 13. 배포 및 초기화

1. DBA가 인증·정책·감사 테이블과 제약조건을 생성한다.
2. 설정 전용 최소 권한 DB 계정을 발급한다.
3. `MONITORING_CONTROL_CONNECTION_STRING`과 세션 쿠키 설정을 배포 환경에
   주입한다.
4. CLI로 최초 `admin` 계정을 대화형 생성한다.
5. 기존 `.env` 일정 값을 DB 정책 초기값으로 명시적으로 이관한다.
6. DB 정책과 기존 대시보드 판정 결과를 비교한다.
7. 로그인 필수 조회를 활성화한다.
8. 관리자 일정 변경과 감사 이력 저장을 검증한다.

초기 이관이 끝나도 `.env` 정책은 장애 fallback 용도로 당분간 유지한다. DB
정책이 안정화된 뒤 운영자가 의도적으로 fallback 값을 갱신하거나 제거할 수 있다.

## 14. 테스트 전략

### 14-1. API

- 비로그인 모니터링 API `401`
- viewer 조회 성공과 수정 `403`
- 관리자 조회·수정 성공
- Argon2id 해시와 평문 비밀번호 비저장
- 세션 유휴·절대 만료, 로그아웃, 비활성화
- CSRF와 Origin 검증
- 로그인 실패 제한과 동일 오류 문구
- 정책 유효성, 중복 일정, 알 수 없는 데이터셋 거부
- rowversion 충돌 `409`
- 정책 UPDATE와 감사 INSERT 원자성
- DB 정책, 캐시, `.env`, 무정책 우선순위
- 일일·주간·복수 회차와 timezone 경계 판정
- 정책 변경이 과거 canonical 상태를 수정하지 않음

### 14-2. 웹

- 비로그인 로그인 화면 이동과 안전한 복귀
- viewer 관리자 편집 기능 미노출
- 관리자 편집·검증·확인·저장
- 세션 만료 처리
- 저장 실패와 `409` 충돌 복구
- 실제 스케줄을 변경하지 않는다는 고정 안내
- 키보드 탐색, 오류 연결, 포커스 이동

### 14-3. 보안

- 쿠키 속성과 HTTPS 강제
- 외부 `returnTo` 차단
- SQL·연결 문자열·비밀번호·세션 토큰 로그 비노출
- 수집 업무 테이블 DML 권한 부재 확인
- 운영 API 문서 비활성화

## 15. 완료 기준

- 로그인하지 않은 사용자는 모니터링 데이터를 조회할 수 없다.
- viewer는 모든 모니터링 정보와 기준 일정을 읽을 수 있지만 수정할 수 없다.
- 관리자는 검증된 기준 일정만 수정할 수 있다.
- 변경은 감사 이력과 하나의 트랜잭션으로 저장된다.
- 실제 Windows 작업 스케줄러와 수집 실행에는 어떤 변경도 발생하지 않는다.
- DB 정책 변경이 API 재시작 없이 상태 판정에 반영된다.
- 정책 DB 장애 시 fallback 출처와 경고가 사용자에게 표시된다.
- 기존 수집 업무 DB 연결의 읽기 전용 보장이 유지된다.
