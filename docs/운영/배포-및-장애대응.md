# 배포 및 장애 대응

## 1. 배포 경계

웹 정적 파일과 FastAPI를 독립 프로세스로 배포한다. API는 내부 인터페이스에만
바인딩하고 TLS와 접근 제어는 reverse proxy에서 종료한다. MVP 로그인은
미구현 상태이며 FastAPI에는 익명 `viewer` 역할과 향후 `operator`/`admin`
검사를 연결할 설계 경계만 있다. 사내망, VPN, 방화벽 allowlist 또는 조직의
인증 proxy 없이 인터넷에 직접 노출하지 않는다.

배포 환경은 다음 원칙을 지킨다.

- FC다움/HMR별 SELECT 전용 DB 계정을 따로 발급한다.
- 각 ODBC 연결 문자열에 `ApplicationIntent=ReadOnly`를 둔다.
- 비밀값은 배포 시스템의 secret store에서 환경변수로 주입하고 파일·이미지·로그에
  넣지 않는다.
- API 시작 명령은 수집기 또는 DB 마이그레이션을 실행하지 않는다.
- API와 웹에는 수집 실행·삭제·수정 경로를 추가하지 않는다.
- 화면은 자동 polling하지 않으며 운영자의 수동 `새로고침`으로만 재조회한다.

## 2. 빌드와 실행

```powershell
npm ci
npm run test
npm run typecheck
npm run lint
npm run build

py -3.12 -m venv apps/api/.venv
apps/api/.venv/Scripts/python.exe -m pip install -e "apps/api[test]"
apps/api/.venv/Scripts/python.exe -m pytest apps/api/tests -p no:cacheprovider
apps/api/.venv/Scripts/python.exe -m uvicorn monitoring_api.main:app `
  --app-dir apps/api/src --host 127.0.0.1 --port 8000
```

운영에서는 테스트 extra 없이 wheel 또는 `pip install apps/api`로 설치해도 된다.
프로세스 관리자에서 비정상 종료 시 재시작을 설정하되, readiness 실패만으로
재시작 루프를 만들지 않는다. DB 장애는 프로세스 장애와 분리해야 한다.

## 3. CORS와 reverse proxy

웹과 API를 다른 Origin으로 제공하면 `MONITORING_CORS_ORIGINS`에 실제 웹
Origin을 정확히 지정한다. 여러 Origin은 쉼표로 구분한다. 허용 메서드는 GET,
허용 요청 헤더는 Authorization뿐이며 credential CORS는 비활성화되어 있다.

동일 Origin 배포를 권장한다. 아래 Nginx 예시는 `/api/`와 `/health/`를 API로,
나머지를 웹 정적 파일로 전달한다.

```nginx
server {
    listen 443 ssl;
    server_name monitoring.example.internal;

    root /srv/collection-monitoring/web;
    index index.html;

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location /health/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

이 경우 빌드 시 `VITE_MONITORING_API_URL=https://monitoring.example.internal`로
설정한다. 브라우저에 내장되는 `VITE_*` 값에는 비밀값을 절대 넣지 않는다.
proxy access/error log에도 Authorization, 연결 문자열, SQL, 응답 본문을
기록하지 않는다.

## 4. 상태 의미와 운영자 조치

| API 상태 | 화면 | 심각도 | 의미 | 운영자 조치 |
| --- | --- | --- | --- | --- |
| `SUCCESS` | 정상 | 정상 | 모든 작업의 최종 시도가 성공하고 신선도가 정상 | 조치 없음. 정기 추세만 확인 |
| `SUCCESS_EMPTY` | 데이터 없음 | 정상 | API와 커밋은 성공했으나 원천 건수가 0 | 해당 기간에 데이터가 없는 것이 정상인지 원천 서비스에서 확인. 반복 시 입력 조건 점검 |
| `WARNING` | 주의 | 주의 | 재시도 후 성공했거나 신선도가 지연 | 상세 시도와 지연 데이터셋 확인. 반복되면 원천 API·네트워크 안정성 조사 |
| `PARTIAL_FAILED` | 부분 실패 | 장애 | 일부 브랜드/채널은 성공하고 일부는 최종 실패 | 실패 단위와 정규화 오류 분류 확인, 성공 적재는 보존하고 실패 수집기 저장소의 운영 절차로 대응 |
| `FAILED` | 실패 | 장애 | 모든 작업 실패 또는 실행 초기화 실패 | 원천 API, 수집기 로그, DB 연결 순서로 즉시 조사하고 담당자 호출 |
| `RUNNING` | 실행 중 | 진행 | 허용 시간 안에서 실행 중 | 예정 실행 시간과 평소 소요시간을 비교. 허용시간 전에는 대기 |
| `ABORTED` | 중단 | 장애 | 허용시간 초과 또는 비정상 종료 | 프로세스/스케줄러 종료 원인과 마지막 커밋 확인. 중복 안전성을 확인한 뒤 수집기 절차에 따라 재실행 판단 |
| `NOT_RUN` | 미실행 | 상태 확인 필요 | 예정 시각 이후 실행 이력이 없음 | 스케줄러, 배포, 계정 만료와 기동 로그를 확인하고 누락 범위를 산정 |

장애 KPI와 장애 심각도에는 `PARTIAL_FAILED`, `FAILED`, `ABORTED`만 포함한다.
`NOT_RUN`은 장애로 집계하지 않지만 예정 실행 누락 여부를 확인하고 원인을 조사해야
하는 상태다. `PARTIAL_FAILED`는 `WARNING`이 아니라 장애다. 상태는 작업별 마지막
시도로 계산되며 실패 뒤 재시도 성공은 `WARNING`이다. 원문 오류는 API에 노출되지
않으므로 `error_category`와 해당 수집기 내부 로그의 요청 식별자를 사용해 추적하되
비밀정보나 응답 본문을 티켓에 복사하지 않는다.

## 5. 헬스 체크 판정

- `GET /health/live`: DB를 조회하지 않고 API 프로세스 생존만 확인한다. 200이
  아니면 프로세스, 포트, reverse proxy를 조사한다.
- `GET /health/ready`: 등록된 모든 DB에 `SELECT 1`을 실행한다. 하나라도 실패하거나
  등록된 소스가 없으면 503이다.
- 모니터링 조회: 한 소스 장애 시에도 200 부분 응답과
  `SOURCE_UNAVAILABLE`을 함께 반환할 수 있다. HTTP 200만 보고 정상으로 판정하지
  말고 `errors` 배열을 확인한다.

로드밸런서는 live와 ready를 구분한다. live 실패 인스턴스는 트래픽에서 제거할 수
있지만, 외부 DB 일시 장애로 ready가 503인 인스턴스를 무한 재시작하지 않는다.

## 6. 장애 대응 순서

### API 또는 proxy 장애

1. proxy를 우회한 `http://127.0.0.1:8000/health/live`와 외부 `/health/live`를
   비교한다.
2. 내부만 성공하면 TLS, proxy route, 방화벽, Host 헤더를 확인한다.
3. 둘 다 실패하면 API 프로세스와 포트 충돌, 배포 artifact, Python 의존성을
   확인한다.
4. 직전 정상 artifact로 API만 롤백한다. 롤백 과정에서 DB 스키마를 되돌리거나
   수집기를 실행하지 않는다.

### readiness 또는 `SOURCE_UNAVAILABLE`

1. 어느 `collector_id`가 실패했는지 확인한다.
2. 해당 `MONITORING_*_CONNECTION_STRING`이 주입되었는지만 확인하고 값을
   출력하지 않는다.
3. ODBC Driver 17, DNS, 방화벽, 인증서, DB 가용성을 확인한다.
4. 계정이 해당 소스의 필요한 테이블을 SELECT할 수 있고 DML/DDL 권한은 없는지
   DBA와 확인한다.
5. `ApplicationIntent=ReadOnly` 오타와 `ReadWrite` 충돌을 확인한다.
6. FC다움이면 080 적용 여부를 DBA에게 확인하고 085 SELECT-only 검증을 먼저
   실행한다. 080을 장애 대응 중 임의 재실행하지 않는다.
7. 정상 소스의 부분 응답은 유지하며, 장애 소스 복구 뒤 화면에서 수동
   `새로고침`한다.

### 화면이 갱신되지 않거나 CORS 오류

1. 화면의 `새로고침`을 누르고 브라우저 개발자 도구의 요청 URL을 확인한다.
2. `VITE_MONITORING_API_URL`은 빌드 시 고정되므로 배포 주소 변경 뒤 웹을 다시
   빌드했는지 확인한다.
3. 웹 Origin과 `MONITORING_CORS_ORIGINS`의 스킴·호스트·포트가 정확히 같은지
   확인한다.
4. 동일 Origin proxy라면 `/api/`, `/health/` location과 SPA fallback 순서를
   확인한다.

### 상태·신선도 이상

1. 실행 상세의 마지막 시도, 성공/실패 단위, 커밋 여부와 오류 분류를 확인한다.
2. API 시각은 UTC, 화면 시각은 Asia/Seoul이라는 차이를 고려한다.
3. `SUCCESS_EMPTY`는 장애로 단정하지 말고 원천 데이터 유무를 먼저 확인한다.
4. `RUNNING` 장기 지속은 허용시간을 넘으면 `ABORTED` 대응으로 전환한다.
5. 모니터링 플랫폼에서 수집을 실행하지 않는다. 재실행이 필요하면 각 수집기
   저장소의 승인된 운영 절차를 사용한다.

## 7. FC다움 배포 전 확인

FC다움 감사 스키마는 다음 순서로만 준비한다.

1. 변경 승인과 백업 정책 확인
2. DBA/마이그레이션 계정으로 `080_create_collection_audit_tables.sql` 적용
3. `085_verify_collection_audit_tables.sql`의 SELECT-only 검증
4. FC다움 전용 읽기 계정으로 085 재검증
5. monitoring 연결 문자열 주입
6. `/health/ready`, collectors, runs 순서의 SELECT-only smoke

085 결과가 불완전하면 API를 연결하지 않고 DB 변경 담당자에게 돌려보낸다.
smoke에서는 수집 명령, 080, DDL/DML을 실행하지 않는다.

## 8. 비밀 유출 대응

연결 문자열 또는 비밀번호가 로그·티켓·화면에 노출됐다고 의심되면 즉시 해당
데이터 소스의 읽기 계정을 회전하고 기존 자격 증명을 폐기한다. 로그에서 값을
검색할 때도 원문을 출력하지 말고 보안 담당 절차를 따른다. 새 secret을 배포한
뒤 API를 재시작하고 `/health/ready`부터 확인한다. 저장소 `.env`, shell history,
빌드 artifact에 비밀이 남지 않았는지도 점검한다.
