# 로컬 실행

## 1. 실행 원칙

이 플랫폼은 FC다움, HMR과 SmartPlace의 감사·업무 테이블을 조회하는 모니터링 전용
애플리케이션이다. API 시작 시 DB 연결을 열거나 수집 작업을 실행하지 않는다.
수집기 연결은 인증된 readiness 또는 모니터링 GET 요청 시 열리고 조회가 끝나면 닫힌다.

MVP에는 수집 실행·재실행·삭제 기능이 없다. 웹도 자동 polling 없이 최초 조회와
사용자의 `새로고침` 동작으로만 API를 다시 호출한다. 아이디·비밀번호 로그인과 쿠키 세션을 사용하며, 조회에는 viewer 권한이 필요하다. 관리자만 별도 제어 DB의 기준 일정을 변경할 수 있다. 수집기 DB는 SELECT 전용으로 유지한다. 인증과 배포 구성은 [로그인 및 기준 일정 운영](로그인-및-기준-일정.md)을 따른다.

## 2. 준비물

- Node.js 22.13.0 이상
- Python 3.12 64비트
- Microsoft ODBC Driver 17 for SQL Server
- FC다움 DB, HMR DB와 SmartPlace naverDB에 각각 발급한 SELECT 전용 계정

적재 계정, 수집기 `.env`, 다른 프로젝트의 자격 증명을 재사용하지 않는다.
FC다움, HMR과 SmartPlace 계정도 서로 분리한다. 각 계정에는 필요한 감사·신선도 테이블과
시스템 카탈로그 조회 권한만 주고 DDL/DML 권한은 주지 않는다.

## 3. 의존성 설치

저장소 루트에서 실행한다.

```powershell
npm install
py -3.12 -m venv apps/api/.venv
apps/api/.venv/Scripts/python.exe -m pip install -e "apps/api[test]"
```

## 4. 환경변수

먼저 [제어 DB 스키마 적용](제어-DB-스키마-적용.md)에 따라 별도 제어 DB를 준비하고 `MONITORING_CONTROL_CONNECTION_STRING`을 설정한다. [로그인 운영 문서](로그인-및-기준-일정.md)의 CLI로 최초 사용자를 생성한다. 앱 런타임은 ADMIN 환경변수만으로 사용자를 자동 생성하지 않는다.

루트의 `.env.example`은 키와 형식만 제공한다. 실제 값은 커밋하지 말고 로컬
`.env` 또는 운영 비밀 저장소에 둔다.

| 변수 | 필수 여부 | 설명 |
| --- | --- | --- |
| `MONITORING_FCDAUM_CONNECTION_STRING` | 소스별 선택 | FC다움 DB SELECT 전용 ODBC 연결 문자열 |
| `MONITORING_HMR_CONNECTION_STRING` | 소스별 선택 | HMR DB SELECT 전용 ODBC 연결 문자열 |
| `MONITORING_SMARTPLACE_CONNECTION_STRING` | 소스별 선택 | naverDB의 SmartPlace 감사 테이블 SELECT 전용 ODBC 연결 문자열 |
| `MONITORING_CORS_ORIGINS` | 브라우저 분리 배포 시 필수 | 허용할 웹 Origin. 스킴·호스트·포트를 포함하고 여러 값은 쉼표로 구분 |
| `VITE_MONITORING_API_URL` | 웹 필수 | 브라우저가 호출할 API 기준 URL |
| `VITE_MONITORING_API_TIMEOUT_MS` | 선택 | 브라우저 요청 제한 시간(양수 밀리초, 기본 40,000) |
| `MONITORING_DB_CONNECT_TIMEOUT_SECONDS` | 선택 | DB 로그인·연결 제한 시간(양수 초, 기본 5) |
| `MONITORING_DB_QUERY_TIMEOUT_SECONDS` | 선택 | SQL statement 제한 시간(양수 초, 기본 30) |
| `MONITORING_SOURCE_TIMEOUT_SECONDS` | 선택 | 어댑터 병렬 조회의 공통 제한 시간(양수 초, 기본 35) |

수집기별 현재 상태 정책은 실제 scheduler와 운영 SLA를 확인한 뒤에만 다음
변수를 설정한다. 임의의 일정을 추측해 넣지 않는다.

| 변수 접미사 | 형식 | 의미 |
| --- | --- | --- |
| `SCHEDULE_TIMEZONE` | IANA timezone | 일일 예정 시각의 기준 timezone |
| `DAILY_SCHEDULED_TIME` | `HH:MM` | 일일 예정 시각 |
| `MAX_DURATION_MINUTES` | 양수 정수 | `RUNNING`을 stale `ABORTED`로 표시할 허용시간 |
| `FRESHNESS_SLA_MINUTES` | `dataset=minutes,...` | 고정 데이터셋별 마지막 변경 시각 SLA |

접두사는 `MONITORING_FCDAUM_` 또는 `MONITORING_HMR_`를 사용한다. 정책을
설정하지 않은 항목은 저장된 run 상태를 그대로 표시한다. 실행 이력의 상태
필터와 건수는 언제나 저장된 run의 canonical 상태를 사용하며, 현재 시각에 따른
`NOT_RUN`, stale `ABORTED`, freshness `WARNING`은 `/collectors` overview에만
적용한다. `SCHEDULE_TIMEZONE`과 `DAILY_SCHEDULED_TIME`은 반드시 함께 설정한다.
신선도 데이터셋 이름은 `.env.example`에 열거된 고정 이름만 허용하며 오타는 API
기동 시 거부한다.

SmartPlace는 연결 문자열과 함께 시간대, 일일 예정 시각, 시작 유예시간, 최대
실행시간과 예상 scope를 모두 설정해야 한다. 이 필수 항목 중 하나만 빠져도 API
기동 시 거부한다. `MONITORING_SMARTPLACE_SCHEDULE_ATTRIBUTION_WINDOW_MINUTES`는
선택 설정이며 기본값은 60분이다. 명시할 때는 시작 유예시간 이상이면서 1일보다
짧아야 한다.

| 변수 | 의미 |
| --- | --- |
| `MONITORING_SMARTPLACE_SCHEDULE_TIMEZONE` | 예정 회차의 IANA timezone |
| `MONITORING_SMARTPLACE_DAILY_SCHEDULED_TIME` | 실제 Windows 예약 작업의 일일 예정 시각 |
| `MONITORING_SMARTPLACE_START_GRACE_MINUTES` | 미실행 판정 전 시작 유예시간 |
| `MONITORING_SMARTPLACE_MAX_DURATION_MINUTES` | 장시간 `RUNNING`을 `ABORTED`로 표시할 기준 |
| `MONITORING_SMARTPLACE_SCHEDULE_ATTRIBUTION_WINDOW_MINUTES` | 선택. 예약 시각 뒤 실행을 해당 회차로 귀속할 최대 창(기본 60분) |
| `MONITORING_SMARTPLACE_EXPECTED_SCOPES` | `scope_id:표시명` 목록. 현재 `hanchon:한촌설렁탕,yuksoodang:육수당` |

API 의존성에는 Windows에서도 IANA timezone을 일관되게 해석할 수 있도록
`tzdata`가 포함된다. source 조회는 수집기별 bulkhead 안의 daemon 작업으로
병렬 실행한다. 한 source가 driver 수준에서 멈추더라도 공통 deadline 뒤 응답을
반환하고, 반복 timeout은 해당 source의 고정 슬롯까지만 차지해 다른 정상 source를
굶기지 않는다. DB 연결·statement timeout과 cursor/connection `finally` 정리는
이 응답 제한과 별도로 계속 적용된다.

연결 문자열에는 `ApplicationIntent=ReadOnly`를 명시한다. 앱도 누락 시 이를
추가하고 `ReadWrite` 값을 거부하지만, 이것은 DB 권한을 대신하지 않는다.

```dotenv
MONITORING_FCDAUM_CONNECTION_STRING=Driver={ODBC Driver 17 for SQL Server};Server=<FCDAUM_SQLSERVER>;Database=<FCDAUM_DATABASE>;UID=<FCDAUM_READONLY_USER>;PWD=<SECRET_FROM_SECRET_STORE>;Encrypt=yes;TrustServerCertificate=no;ApplicationIntent=ReadOnly
MONITORING_HMR_CONNECTION_STRING=Driver={ODBC Driver 17 for SQL Server};Server=<HMR_SQLSERVER>;Database=<HMR_DATABASE>;UID=<HMR_READONLY_USER>;PWD=<SECRET_FROM_SECRET_STORE>;Encrypt=yes;TrustServerCertificate=no;ApplicationIntent=ReadOnly
MONITORING_SMARTPLACE_CONNECTION_STRING=Driver={ODBC Driver 17 for SQL Server};Server=<NAVER_SQLSERVER>;Database=naverDB;UID=<SMARTPLACE_READONLY_USER>;PWD=<SECRET_FROM_SECRET_STORE>;Encrypt=yes;TrustServerCertificate=no;ApplicationIntent=ReadOnly
MONITORING_SMARTPLACE_SCHEDULE_TIMEZONE=Asia/Seoul
MONITORING_SMARTPLACE_DAILY_SCHEDULED_TIME=04:00
MONITORING_SMARTPLACE_START_GRACE_MINUTES=15
MONITORING_SMARTPLACE_MAX_DURATION_MINUTES=180
MONITORING_SMARTPLACE_SCHEDULE_ATTRIBUTION_WINDOW_MINUTES=60
MONITORING_SMARTPLACE_EXPECTED_SCOPES=hanchon:한촌설렁탕,yuksoodang:육수당
MONITORING_CORS_ORIGINS=http://localhost:5173
VITE_MONITORING_API_URL=http://localhost:8000
VITE_MONITORING_API_TIMEOUT_MS=40000
MONITORING_DB_CONNECT_TIMEOUT_SECONDS=5
MONITORING_DB_QUERY_TIMEOUT_SECONDS=30
MONITORING_SOURCE_TIMEOUT_SECONDS=35
```

수집기 연결 변수 중 일부만 설정하면 해당 소스만 등록된다. 모두 없으면 API는
기동되지만 관리자 인증 후 readiness는 503이다. Pydantic 설정의 연결 문자열 필드는 마스킹되며,
API 오류 응답에는 연결 문자열, SQL 원문, 원문 예외를 포함하지 않는다.

API를 저장소 루트에서 실행할 때는 루트 `.env`를 읽는다. Vite는
`apps/web`을 환경 루트로 사용하므로 웹 URL은 다음 중 하나로 전달한다.

```powershell
# 방법 1: 현재 셸에만 주입
$env:VITE_MONITORING_API_URL = "http://localhost:8000"

# 방법 2: apps/web/.env.local에 VITE_MONITORING_API_URL 한 줄 저장
```

`.env.local`도 실제 배포 주소가 들어갈 수 있으므로 커밋하지 않는다.

## 5. FC다움 감사 테이블 준비

FC다움 모니터링을 처음 연결할 때만 다음 순서를 지킨다.

1. DBA 또는 승인된 마이그레이션 계정으로 대상 DB와 `dbo` 스키마를 확인한다.
2. `C:\workspace\fcdaum_crawling\sql\080_create_collection_audit_tables.sql`을
   적용한다. 이 파일은 DDL이므로 모니터링 SELECT 전용 계정으로 실행하지 않는다.
3. `C:\workspace\fcdaum_crawling\sql\085_verify_collection_audit_tables.sql`을
   실행한다. 085는 테이블·컬럼·인덱스·제약조건·최근 이력만 읽는 SELECT-only
   검증이다.
4. 두 감사 테이블과 PK·인덱스, 예상 컬럼이 모두 조회되는지 확인한다.
5. 그 뒤 FC다움 SELECT 전용 계정으로 085를 다시 실행해 실제 조회 권한을
   검증하고 `MONITORING_FCDAUM_CONNECTION_STRING`을 주입한다.

080 적용과 085 확인 과정에서 수집기는 실행하지 않는다. HMR은 기존
`CHANNEL_COLLECTION_RUN`, `CHANNEL_COLLECTION_ATTEMPT`와 주문 신선도 테이블을
사용하므로 스키마 생성 없이 HMR 전용 SELECT 계정의 조회 권한만 확인한다.

## 6. SmartPlace 감사 테이블 준비

SmartPlace를 처음 연결할 때는 승인된 DBA가 naverDB에서 다음 순서를 지킨다.

1. `scripts/sql/smartplace_monitoring/01_create.sql`의 대상 DB 방어문, 두 테이블,
   제약조건과 트랜잭션을 사전 검토한다. 파일은
   `C:\workspace\naver_crawling` 저장소에 있다.
2. 백업·변경 승인을 확인한 뒤 DBA 또는 마이그레이션 계정으로 naverDB를 명시해
   `01_create.sql`을 적용한다. 모니터링 SELECT 전용 계정으로 DDL을 실행하지 않는다.
3. `scripts/sql/smartplace_monitoring/02_verify.sql`을 실행해
   `SMARTPLACE_COLLECTION_RUN`, `SMARTPLACE_COLLECTION_ATTEMPT`, 기본키·고유키·외래키와
   CHECK 제약조건을 확인한다. 이 파일은 시스템 카탈로그만 읽는 SELECT-only 검증이다.
4. SmartPlace 크롤러 실행 계정에는 두 테이블의 필요한 `SELECT`, `INSERT`, `UPDATE`만,
   대시보드 API 계정에는 `SELECT`만 별도로 부여한다. API 계정에는 DDL/DML 및
   스케줄러 권한을 부여하지 않는다.
5. 대시보드 계정으로 `02_verify.sql`을 다시 실행해 실제 조회 권한을 검증한 후에만
   연결 문자열을 주입한다.

이 단계에서는 크롤러, 브라우저, Windows 예약 작업을 실행하지 않는다. 전체 운영
절차는 `docs/운영/smartplace-사후-모니터링.md`를 따른다.

## 7. API와 웹 실행

터미널 1에서 API를 실행한다.

```powershell
apps/api/.venv/Scripts/python.exe -m uvicorn monitoring_api.main:app `
  --app-dir apps/api/src --host 127.0.0.1 --port 8000
```

터미널 2에서 웹을 실행한다.

```powershell
npm run dev --workspace=@collection-monitoring/web
```

브라우저에서 `http://localhost:5173`을 연다. 개발 서버 Origin이 달라지면
`MONITORING_CORS_ORIGINS`도 정확히 같은 Origin으로 바꾸고 API를 다시 시작한다.
와일드카드 Origin은 사용하지 않는다.
API 설정은 `*`, HTTP(S)가 아닌 값, userinfo·path·query·fragment가 포함된 값을
기동 시 거부한다.

## 8. 안전한 로컬 확인

먼저 DB와 무관한 liveness만 확인한다.

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health/live
```

예상 응답은 `status`가 `ok`인 JSON이다. 이 결과는 DB 준비 완료를 뜻하지 않는다.

전용 연결 문자열과 제어 DB가 준비된 경우에만 아래 요청을 확인한다. 먼저 같은 호스트(localhost)의 웹에서 로그인하고 인증 쿠키를 포함해야 한다. readiness는 admin, 모니터링 조회는 viewer 권한이 필요하다. 인증되지 않은 요청은 401이며, 제어 DB 장애 시 보호 API는 503으로 차단된다. 로그인·세션 처리는 제어 DB에 기록을 쓰며 수집기 데이터 조회는 SELECT 전용이다.

```powershell
curl.exe --fail-with-body --cookie "<인증된 세션 쿠키 파일>" http://localhost:8000/health/ready
curl.exe --fail-with-body --cookie "<인증된 세션 쿠키 파일>" http://localhost:8000/api/v1/monitoring/collectors
curl.exe --fail-with-body --cookie "<인증된 세션 쿠키 파일>" "http://localhost:8000/api/v1/monitoring/runs?page_size=5"
```

예상 결과는 readiness 200, 설정된 `fcdaum`/`hmr`/`smartplace` 항목의
`ready: true`, 그리고
collectors/runs의 200 JSON 응답이다. 등록된 수집기의 감사 이력이 아직 없으면
`/collectors`는 `latest_run: null`인 overview를 반환할 수 있으며, 명시된 예정
시각을 지났다면 상태는 `NOT_RUN`이다. 이는 DB 장애와 구분된다.

`/summary`는 Asia/Seoul의 오늘 자정 경계를 사용해 정상 실행
(`SUCCESS`, `SUCCESS_EMPTY`), 장애 실행(`PARTIAL_FAILED`, `FAILED`, `ABORTED`),
실행 중 건수를 각각 반환한다. 전체 상태도 같은 오늘 집계의 가장 높은 장애 등급을
사용한다. `/collectors`는 한 source snapshot 안에 신선도 목록을 함께 반환하므로
웹은 별도 `/freshness` 중복 조회 없이 이를 표시한다. 호환용 `/freshness`도 같은
필드 계약을 유지한다. `last_successful_check_at`은 마지막 성공 확인 시각이고
`latest_data_at`은 실제 데이터가 마지막으로 바뀐 시각이므로 두 값을 같은 의미로
해석하지 않는다.

수집기 연결 문자열이 없다면 실제 수집기 DB smoke를 수행하지 않는다. 제어 DB와 관리자 인증이 정상인 상태에서 소스 미등록 응답은
다음과 같다.

```text
GET /health/ready -> 503
{"status":"unavailable","items":[],"errors":[{"collector_id":"configuration","code":"SOURCE_UNAVAILABLE","message":"등록된 모니터링 데이터 소스가 없습니다."}]}
```

이때 모니터링 조회는 HTTP 200이어도
`source_status.all_sources_unavailable: true`를 반환한다. 등록 소스가 0개이거나
등록 소스 조회가 모두 실패한 경우 웹은 전체 오류 화면을 표시한다. 한 소스만
실패하고 다른 소스가 응답하면 `succeeded`와 `failed` 건수를 함께 제공하고 웹은
부분 장애로 표시한다. 테스트 fixture나 mock 결과를 실제 smoke라고 기록하지
않는다.

## 9. 로컬 검증 명령

```powershell
apps/api/.venv/Scripts/python.exe -m pytest apps/api/tests -p no:cacheprovider
npm test
npm run typecheck
npm run lint
```
